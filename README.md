# LuxTriangleAttention.jl

<p align="center">
  <img src="assets/logo.svg" alt="LuxTriangleAttention.jl logo" width="200">
</p>

Triangle Attention and Triangle Multiplication layers for [Lux.jl](https://github.com/LuxDL/Lux.jl), built for protein structure prediction models such as AlphaFold and Boltz.

## Benchmarks

Runtime of the `Attention` layer (pair-bias, `bias_layout=:kq`) vs. the OpenFold-3 PyTorch reference, across Julia CPU (+ AppleAccelerate), Julia GPU (Metal.jl), Reactant/XLA (CPU and GPU via the jax-mps PJRT plugin), and PyTorch (CPU and MPS). Lower is better.

For any number of residues N, XLA-optimized julia code outperforms the PyTorch implementations on both CPU (10-20%) and Metal GPU (roughly 2x).

## Features

- **Triangle Attention** — Starting and Ending axial attention with triangle bias (AlphaFold2 Algorithms 13 & 14).
- **Triangle Multiplication** — Outgoing and Incoming triangle multiplication (AlphaFold2 Algorithms 11 & 12).
- Built natively on `Lux.jl`, using `Lux.scaled_dot_product_attention` and `Lux.batched_matmul` for performance.
- Gated attention and Gated Linear Units (GLU / SwiGLU) support.
- Fused flash-attention kernels for Apple (Metal) and NVIDIA (CUDA) GPUs, scalar and on the matrix units, in Float32, Float16 and BFloat16; see [GPU backends](#gpu-backends).
- Numerically verified against reference PyTorch implementations (AlphaFold2, AlphaFold3, Boltz2) across precisions and input configurations.

using Pkg

## GPU backends

The fused attention kernels (`use_kernel=static(true)`, see the [fused kernels tutorial](https://janssena.github.io/LuxTriangleAttention.jl/dev/tutorials/2-fused-kernels/)) run on Apple GPUs and on NVIDIA GPUs. Load the package for your GPU next to this one and the kernels are found by themselves (they are Julia package extensions):

```julia
using Lux, LuxTriangleAttention, Metal   # Apple GPU
using Lux, LuxTriangleAttention, CUDA    # NVIDIA GPU, sm_80 (Ampere) and newer for the tensor-core kernel
```

| | Metal | CUDA |
|:--|:--|:--|
| `:default`, the scalar flash kernel | Float32, Float16, BFloat16 | Float32, Float16, BFloat16 |
| `:flash_mma`, the matrix-unit kernel | 8×8 `simdgroup_matrix` products | tensor cores (`mma.sync` m16n8k16), Ampere (sm_80) and newer |
| `:flash_mma` head dimension | a multiple of 8 | a multiple of 16; other heads (the AlphaFold size 8) run `:default` |
| `:flash_mma` Float32 data | computed in Float32 | computed at Float16, see below |

Select the matrix-unit kernel with `use_kernel!(:flash_mma)`; `:default` runs otherwise. Both keep every accumulator in Float32 and return the types you passed in.

- **Float32 on an NVIDIA GPU.** The tensor cores take 16-bit operands, so `:flash_mma` rounds Float32 inputs to Float16 inside the call (values beyond ±65504 saturate instead of overflowing, so a bias of `-1e9` still means "masked") and returns Float32. Expect Float16-level accuracy (about 1e-3 relative); `:default` keeps Float32 exact.
- **Unsupported cases run `:default`** with a one-time message: a head dimension the matrix units cannot contract over, a type they cannot take, a GPU older than sm_80.
- **Tuning.** The first call for a data type, head dimension and length tunes the kernel on your device (seconds to minutes, verified against a reference) and caches the result under `~/.cache/KernelDispatch` (`KERNELDISPATCH_CACHE` moves it). Tune ahead of time with `tune_flash_kernel!` / `tune_flash_mma!`, and always before compiling with Reactant, which cannot tune mid-trace. Give concurrent sessions their own cache directory: they otherwise delete each other's binaries.
- **Speed.** On an NVIDIA A40 (triangle attention shapes, 4 heads, n = 128–384) `:flash_mma` is 1.5–2.3× faster than `:default` in Float16 and 2.4–4.4× in BFloat16, forward; the backward gains are 1.7–3.3×. Float32 gains 1.1–1.6× (including the conversions). The kernels reach roughly 10–17 TFLOP/s there, well below the tensor-core peak: this is a first version, written for correctness. The benchmark is `test/bench/kernels/cuda.bench.jl`.
- **Compiling with Reactant on NVIDIA.** Fused kernels in a Reactant-compiled program need KernelDispatch 0.2.1 or newer, which
  declares the custom call's operand layouts (0.2.0 does not, and XLA can then hand the kernel a transposed bias: the result
  is wrong, silently). XLA also multiplies Float32 matrices at TF32 precision by default; the [Reactant tutorial](https://janssena.github.io/LuxTriangleAttention.jl/dev/tutorials/3-reactant/) shows how to ask for full Float32.
- **Other backends.** KernelDispatch.jl also has a ROCm tag. A backend is a handful of methods (device limits, an array constructor, an atomic add and the matrix-unit hooks, `ext/LuxTriangleAttentionCUDAExt/` is the template).

## Quick Start

### Triangle Attention

```julia
using Lux, LuxTriangleAttention, Random

# [Channels, Ni, Nj, Batch]
x = randn(Float32, 64, 32, 32, 1)

model = TriangleAttention(
    64,      # input channels
    32,      # head dimension
    4;       # number of heads
    is_starting=true # true for Starting Node, false for Ending Node
)

rng = Random.default_rng()
ps, st = Lux.setup(rng, model)

y, st = model(x, ps, st)
```

### Triangle Multiplication

```julia
model = TriangleMultiplication(
    64,      # input channels
    128,     # hidden channels
    is_outgoing=true # true for Outgoing, false for Incoming
)

y, st = model(x, ps, st)
```

## Layer Details

### Triangle Attention
Axial attention over the pair representation, incorporating a triangle bias:
- **Starting Node**: attends over the $j$ dimension.
- **Ending Node**: attends over the $i$ dimension.

Input shape is `[C, Ni, Nj, B]`, queries are `[D, H, Ni, Nj, B]`. This implementation attends over the **3rd** dimension (`token_dim=3`), which differs from some Python implementations (e.g. AlphaFold, Boltz) that attend over the 4th.

### Triangle Multiplication
Updates the pair representation by combining edges sharing a common node:
- **Outgoing**: $`\mathbf{z}_{ij} = \sum_k \mathbf{a}_{ik} \odot \mathbf{b}_{jk}`$
- **Incoming**: $`\mathbf{z}_{ij} = \sum_k \mathbf{a}_{ki} \odot \mathbf{b}_{kj}`$

## Masking and Bias

### Boolean Masking
Masks of shape `[N, B]`, `[Ni, Nj, B]`, or `[N, S, B]` are reshaped automatically to fit the internal attention score format.

```julia
# Sequence padding mask, [N, B]
mask = rand(Bool, 32, 1)
y, st = model((; x, mask), ps, st)

# Pairwise mask, [Ni, Nj, B]
mask_ij = rand(Bool, 32, 32, 1)
y, st = model((; x, mask=mask_ij), ps, st)
```

### Attention Bias and Layouts (`prep_bias`)

`prep_bias` shapes a custom attention bias tensor according to the `Attention` layer's `bias_layout`:

- **`bias_layout=:qk`** — symmetric/triangle layout, used by `TriangleAttention`. Input `[C, Ni, Nj, B]`, bias `[H, Ni, Nj, B]`, permuted internally to `[Ni, Nj, H, 1, B]`.
- **`bias_layout=:kq`** — asymmetric/pair layout, matching the `AttentionPairBias` module in the AlphaFold3/Boltz Python references. Input `[C, N, S, B]`, bias `[H, Nq, Nk, B]`, permuted/transposed internally to `[Nk, Nq, H, 1, B]`.

```julia
x = randn(Float32, 16, 32, 32, 1)
bias = randn(Float32, 4, 32, 32, 1)

bias_qk = prep_bias(bias, x, :qk) # [Ni, Nj, Heads, 1, Batch]
bias_kq = prep_bias(bias, x, :kq) # [Nj, Ni, Heads, 1, Batch]

# Or pass through the layer directly (prep_bias is called internally)
y, st = model((; x, bias), ps, st)
```

## Custom kernels

The kernel machinery — registry, selection, eager launch, embedding a kernel in a Reactant-compiled
program, the Enzyme rule — lives in [KernelDispatch.jl](https://github.com/Janssena/KernelDispatch.jl) (a registered package, `0.2`), where attention is one declared
op, `SDPA`. KernelDispatch is generic: the same declaration mechanism works for any operation.

Bringing your own compiled forward/backward attention kernels (`.metallib`, `.cubin`/`.ptx`) is covered in the
[documentation](https://janssena.github.io/LuxTriangleAttention.jl/dev/tutorials/5-custom-kernels/): the
kernel type and its `forward`/`backward`, the argument-type `signature`, and pinning your argument lists. The
shapes, element types and offsets your kernel reads are on the
[Kernel operands](https://janssena.github.io/LuxTriangleAttention.jl/dev/kernel-operands/) page.

## Testing

The tests are in `test/` and mirror `src/`: `test/layers/attention.test.jl` tests `src/layers/attention.jl`,
`test/layers/attention.af2.test.jl` compares the same layer with AlphaFold2's PyTorch version (also `af3`, `boltz2`),
`attention.gpu.test.jl` needs the machine's GPU (Metal or CUDA; the tests use only the names its adapter in
`test/ext/<backend>/backend.jl` defines). What is traced by Reactant is in `test/ext/reactant/`, and what is specific to one GPU
backend in `test/ext/<backend>/`. A run can be limited by *component* (the src file, or a group: `kernels`,
`layers`, `ext`), by *backend* (`cpu`, `gpu`, `reactant`) and by Python *model*; the axes combine:

```
julia --project=test test/runtests.jl                        # everything
julia --project=test test/runtests.jl kernels gpu            # the kernel tests that run on the GPU
julia --project=test test/runtests.jl attention af3 cpu      # AlphaFold3 attention parity, on the host
```

From Julia, `Pkg.test("LuxTriangleAttention"; test_args=["attention", "cpu"])`. The pkg REPL's `test` takes no arguments;
set `ENV["LTA_TEST"] = "attention cpu"` first. The parity units compare with the outputs of the Python references, recorded in `test/fixtures/python/` (the lazy artifact
`python_fixtures`, downloaded on first use); Python itself only runs to record them again, see `test/python/README.md`. The GPU is found when a `gpu` unit is selected
(`LTA_TEST_GPU=none|metal|cuda` overrides it), the traced kernel tests run only if one was found, and without one those
units are skipped with a note. On Metal, tracing kernels needs the jax-mps PJRT plugin: set `JAX_MPS_PLUGIN` to the path of
`libpjrt_plugin_mps.dylib` (there is no default location), otherwise those tests are skipped with a warning; the eager Metal
tests do not need it. NVIDIA GPUs need nothing extra: Reactant's own client is used. Run the GPU suites with a private kernel cache, `KERNELDISPATCH_CACHE=$(mktemp -d)`: the tuned
binaries are a shared on-disk registry, and two concurrent sessions delete each other's. The tokens and how they combine are documented in `test/sections.jl`.
