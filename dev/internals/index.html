Internals

The docstrings of everything that is neither exported nor public: the attention routing, the tuner, the stage launcher and the kernel sources. Documented for people reading or extending the package, and not covered by any compatibility promise. The Kernel operands page explains the data these functions move around.

LuxTriangleAttention.DO_SCALE — Constant
DO_SCALE

The large-dO sanity check of the backward stages: the verification problem again with dO (and so delta and every gradient) scaled by 256, a power of two, exact in every storage type; its largest dO entry is then ~1e3. The errors are relative, so the scale cancels.

What it does NOT decide: whether a Float16 dS = P·(dP − δ) can overflow is a property of the INPUTS — it needs peaked attention (P near 1/2…1) together with a large aligned |v|·|dO| (|dP| ≤ dim · max|v| · max|dO|) — not of the configuration. On this random problem P is spread over ~67 keys and Float16 dS stays far from overflow even at dO ~ 2e4 (measured on an M1 Pro). Float16 operands are the FlashAttention-2 convention and carry its caveat: a loss-scaled dO large enough to push dS past 65504 gives non-finite gradients, as it would there.

LuxTriangleAttention.FlashMMA — Type
FlashMMA

:flash_mma: the flash-attention kernel on the GPU's MATRIX units, built by tune_flash_mma!.

MMA is matrix multiply-accumulate: the hardware operation C += A·B on a small tile (8×8 simdgroup_matrix on Metal; tensor cores on NVIDIA). A simdgroup owns a block of query rows and computes Q·Kᵀ and P·V (and the backward products) a fragment at a time; only the row-wise softmax reductions run on the lanes that hold the fragments. The fragment operations are per-backend hooks (flash_mma/), Metal's in the extension. Contrast FlashScalar, which uses plain per-thread arithmetic.

source
LuxTriangleAttention.FlashScalar — Type
FlashScalar

:default: this package's flash-attention kernel with SCALAR arithmetic, built by tune_flash_kernel!.

Each thread owns one query. A threadgroup stages a tile of keys and values in local memory and every thread walks it with ordinary fused multiply-adds, keeping its running softmax state and output row in registers; the work is spread over queries, never over the matrix units. Contrast FlashMMA, which computes the same algorithm on the GPU's matrix units. Both are written in KernelAbstractions; what differs is how the products are computed. The tuned parameters are the threadgroup size tg, the key-tile size kt and the sub-block size sb (flash/).

LuxTriangleAttention._chunked_sdpa — Method
_chunked_sdpa(chunk_size, q, k, v, mask, bias)

Scaled dot-product attention, optionally split into chunk_size slices along dim 4 of q — the first axis the attention batches over, since dim 3 is the token axis being attended.

For a pair input [C, Ni, Nj, B] dim 4 is Nj (a TOKEN axis, not the sample batch), and the scores are [Nq, Nk, H, Nj, B] = O(N³·H) — ~1 GiB per op at N=400. Splitting it bounds the live score tensor to chunk_size · N² · H with no change to the result, and does so at B == 1. Mirrors chunk_size_tri_attn in the openfold/boltz references.

Operands are sliced only when they actually span the chunked axis (size(·, 4) == L); a broadcast axis of size 1 — which is what prep_bias produces for the :qk layout — is passed through whole.

source
LuxTriangleAttention._chunked_sdpa_unrolled — Method
_chunked_sdpa_unrolled(chunk_size, q, k, v, mask, bias)

Chunked attention as an ordinary Julia loop. Executed sequentially it bounds the live score tensor, which is the intended win on the native path — measured at N=512 on one PairformerLayer: 3.2 GB less peak for ~12% more time.

Under Reactant.@compile this loop is UNROLLED into the graph, and because the chunks are mutually independent XLA is free to schedule them concurrently and keep every slice live, completely negating any memory benefits. The Reactant extension therefore overrides _chunked_sdpa with a rolled @trace loop; this method stays the native path and the fallback for chunk sizes the rolled form cannot take.

LuxTriangleAttention._warn_chunking_on_gpu — Method
_warn_chunking_on_gpu(backend)

Say once, on a device backend, that chunking is the wrong tool here.

chunk_size exists because the host path materialises the whole [Nq, Nk, H, Nj, B] score tensor and has no other way to bound it. A fused kernel tiles the keys internally and never materialises it at all, so on a GPU chunking pays the memory cost it was meant to avoid AND serialises work the device would otherwise run at once. Reaching here with device arrays almost always means use_kernel was left at its default rather than that chunking was wanted.

Uses backend_of rather than a GPUArrays dependency: the trait already distinguishes MtlArray, CuArray and ROCArray, and it additionally covers a traced array on a GPU client, which an array type check would miss entirely.

LuxTriangleAttention._with_dead_rows — Method
_with_dead_rows(sdpa, q, k, v, mask, bias)

sdpa(q, k, v, mask, bias) with the behaviour of a FULLY MASKED key set pinned down. Masked logits are -Inf in LuxLib, so a query whose keys are all masked softmaxes over -Inf and comes out NaN. OpenFold and Boltz2 add a large FINITE negative (1e9·(mask - 1)) instead, which makes every logit of such a row equal, so the row attends uniformly and returns the MEAN of v; this does the same, exactly and in any precision: the output of a dead (outer index, batch) slice is the mean of v over the keys, and its gradient reaches v (dO / n per key) but not q, k or bias, the logits having been replaced. The fused kernels follow the same rule, see SDPA.

Done around sdpa rather than inside it: the dead slices are given an all-live mask, so sdpa stays finite there (its NaN would otherwise poison the gradient through the ifelse: 0 * NaN), and their output is then replaced. mask is [n_keys, 1, 1, …] (true = keep), so a slice is dead when any(mask; dims=1) is false.

LuxTriangleAttention.build_stage — Method
build_stage(kernel, stage, T, dim, p; hasbias=true, hasmask=true) -> KernelDispatch.KernelBinary

Compile one stage of a built-in kernel at the parameter point p (a NamedTuple of its tuned parameters) for the loaded device backend, or return the binary already built this session. Its tile is (stage_rows(kernel, p), 1, 1), so a launch of extent = (n, nouter, heads) dispatches (cld(n, rows), nouter, heads) groups. hasbias = false / hasmask = false select the specialisation that never reads the bias / mask (the kernels' HB/HM flags).

T, dim and the parameters are compile-time constants, so each is a separate compilation (the tile loops unroll against them); n and the head count are runtime arguments, so one binary covers every length. Cold compilation is 0.2–0.9 s. The binary records its signature (the stage's kernel_argtypes / mma_argtypes without the Vals) and ka_compile names the file after those types, so a Float16 build is never served for a Float32 request, and a launch that binds other types than it was built for is refused rather than computing garbage.

LuxTriangleAttention.flash_bwd_delta — Method
flash_bwd_delta(o, dO) -> Array{Float32}

delta[j,i,bh] = Σ_d o[d,j,i,bh] * dO[d,j,i,bh], shape matching lse, the row constant both backward kernels need (Σ_j p_{j,kk}(dP_{j,kk} - delta_j) = 0 is the softmax-Jacobian identity that makes dS = p * (dP - delta) correct; see e.g. the FlashAttention-2 paper).

Ordinary broadcasting, not a @kernel: the RESULT costs nothing extra to materialise (it is exactly the shape of o/dO reduced over one axis already the same size as lse), so a raw-pointer kernel buys nothing here. Works on any array backend — CPU, MtlArray, whatever q/k/v already are, for the same reason SDPA()'s CPU fallback needs no device-specific kernel of its own either, see src/kernels/sdpa_op.jl.

Written as a FUSED reduction rather than the obvious sum(Float32.(o) .* Float32.(dO); dims=1), because that form materialises the PRODUCT in full before reducing it away: one extra [dim, n, n, bh] buffer, 134 MB at N=512. Fusing is also ~3.4x faster, since the temporary is never written and read back.

Two details that are easy to get wrong:

  • The broadcast must be instantiated. mapreducedim! calls check_reducedims, which asks the source for axes(A, i), and an un-instantiated Broadcasted has no axes yet.
  • The multiply is done in Float32 explicitly, via the lambda, rather than by broadcasting Float32 over each operand first. For T = Float32 these agree, but for a narrower storage type broadcasted(*, o, dO) would multiply in T and only widen on the way into the accumulator, silently losing the precision the file header requires (see note 3 in forward.jl). Both operands are widened BEFORE the multiply, exactly as the unfused version did. Still lazy, so this costs no memory.

Base.mapreducedim! accepts a Broadcasted source on CPU and GPU alike (Base's own AbstractArrayOrBroadcasted), so the fusion does not cost portability.

LuxTriangleAttention.flash_bwd_dk! — Method
flash_bwd_dk!(dk, q, k, v, bias, mask, dO, lse, delta,
    scale, n, nouter, nh, mheads, Val(T), Val(DIM), Val(TG), Val(KT), Val(HB), Val(HM))

Backward pass, dK, one thread per KEY, streaming query tiles. The transposed geometry of flash_bwd_dq!: q/dO (plus lse/delta) are staged into local memory instead of k/v, and the thread-resident registers hold this key's own k/v instead of q. bias is the ordinary keys-fastest layout, which is the coalesced one for a thread per key.

dK[:, kk, i, bh] is written once, by the thread that owns kk, no atomics, same reasoning as dQ above. Does NOT touch dBias; see the file header.

Holds kv, vv and the dkv accumulator, 3*DIM registers, the same footprint as flash_bwd_dq!. vv is resident here, and absent from flash_bwd_dv!, because dK alone needs dp = v·dO in order to form ds. That asymmetry is the entire reason the two are separate kernels rather than one: see the register-pressure note in the file header.

A masked key contributes nothing at any query of a slice that has a live key (in the forward, p = 0 there for every column; a slice with none attended uniformly, and dV gives every key its share, see flash_bwd_dv!), so dK is written as ZERO for it — selected at the store, not multiplied in, so a non-finite accumulator (a fully-masked row's lse = -Inf) cannot leak through as 0 * Inf = NaN — and never by an early return, since every thread in a group must still take part in the cooperative staging and its @synchronize calls regardless of its own mask value. A query past n in a ragged tile has its staged lse set to +floatmax, which makes its p exactly zero: no branch in the loop.

source
LuxTriangleAttention.flash_bwd_dq! — Method
flash_bwd_dq!(dq, dbias_t, q, k, v, bias_t, mask, dO, lse, delta,
    scale, n, nouter, nh, mheads, Val(T), Val(DIM), Val(TG), Val(KT), Val(HB), Val(HM))

Backward pass, dQ/dBias half: one thread per query, the same grid geometry as flash_fwd! (and the same tile-staging of k/v and of the key mask).

dQ[:, js, i, bh] is written once, at the end, by the thread that owns js, no atomics. dBias is accumulated across the key-tile loop via _atomic_fadd!: the address is shared by every i (bias has no i axis), so nouter threads across different groups can land on it, but never more than nouter, queries and keys otherwise sole-own their contribution. dbias_t is the gradient of bias_t, i.e. in the transposed [n (queries), n (keys), bh] layout, which is what makes a SIMD group's 32 atomics land on 32 consecutive addresses.

A dead key (masked, or past n) is skipped outright. Its staged mask term is shared by the whole group, so the branch is uniform — no divergence — and it saves the atomic as well as the arithmetic.

dbias_t MUST be zeroed by the caller before launch; dq need not be (every active thread's location is fully overwritten, exactly as the forward writes o). With HB = false neither bias_t nor dbias_t is touched.

LuxTriangleAttention.flash_bwd_dv! — Method
flash_bwd_dv!(dv, q, k, bias, mask, dO, lse,
    scale, n, nouter, nh, mheads, Val(T), Val(DIM), Val(TG), Val(KT), Val(HB), Val(HM))

Backward pass, dV, one thread per KEY, streaming query tiles, the same geometry and masking rules as flash_bwd_dk!.

dV[:, kk] = Σ_j p_{j,kk} dO_j needs only the softmax weight p, never dp and never delta. So this kernel takes NEITHER v NOR delta as an argument, they are absent from the signature rather than merely unused, so nothing binds a buffer the kernel never reads, and it holds only kv plus the dvv accumulator: 2*DIM registers, the same footprint as flash_fwd!.

That is what the split buys, and it is why dV rather than dK is the half worth separating; see the register-pressure note in the file header. The s/p recomputed here duplicates flash_bwd_dk!'s, which is pure ALU and repaid many times over by not spilling.

LuxTriangleAttention.flash_fwd! — Method
flash_fwd!(o, lse, q, k, v, bias_t, mask, scale, neg_inf, n, nouter, nh, mheads,
    Val(T), Val(DIM), Val(TG), Val(KT), Val(SB), Val(HB), Val(HM))

Fused attention forward: online softmax over key tiles, one thread per query.

unsafe_indices=true drops KernelAbstractions' implicit __validindex guard. That is deliberate and safe: the kernel does its own bounds handling via active = j < n, and dropping the guard is what allows the sequence length to be a runtime argument rather than baked into the compiled code.

Threads past the end must NOT return early, they still take part in the cooperative tile load and, critically, in the barriers. They are given a clamped index so every address stays in bounds and their result is simply never stored. This is what makes the kernel correct at ANY n, with no padding to a multiple of the tile size.

Algorithm

Per key tile of KT keys, the group stages k, v and the tile's key mask into local memory; each thread then walks the tile in SUB-BLOCKS of SB keys. A sub-block's SB scores are formed first, their maximum updates the running maximum ONCE, and the accumulator is rescaled once — rather than once per key, which costs a full DIM-wide multiply and a second exponential per key. SB trades that saving against SB extra live registers and is tuned per device (see flash/tune.jl).

Softmax runs in base 2: scale·log2(e) is folded into q once and log2(e) into each bias value, so every exponential is a bare exp2. lse is converted back to the natural log on the way out.

The key mask is staged as an ADDITIVE term, 0 for a live key and neg_inf (a large FINITE negative, -floatmax) for a masked one or one past n, so the inner loop has no branch. A masked key then has p = exp2(≈ -floatmax - m) = 0 exactly wherever its row has a live key. A row whose leading keys are all masked accumulates finite garbage until its first live key arrives, and that key's correction factor exp2(≈ -floatmax - m_live) = 0 wipes it exactly. A row with NO live key never leaves m ≈ neg_inf: every score is neg_inf exactly (the real score is absorbed, |s| ≪ ulp(floatmax)), so every key, live or past n, has p = 1, and the accumulator holds Σₖ vₖ (keys past n stage v = 0). It is detected at the end and written as UNIFORM attention, o = Σₖ vₖ / n (the mean of v, what OpenFold's and Boltz2's finite -1e9 mask gives such a row; LuxLib's -Inf would give NaN) and lse = -Inf, the marker the backward reads. The branch is after the key loop, so the hot loop is the same code as without it.

Layout

n is the attended length (queries = keys) and nouter the OUTER length the attention is batched over. They are equal for triangle attention ([C, N, N, B]), and differ for everything else: MSA row attention attends over n = N_res for each of nouter = N_seq rows, column attention the reverse, and a plain [C, N, B] sequence has nouter = 1.

q, k, v, o are [DIM, nh, n, nouter, B] with DIM fastest and element type T, where nh is the number of heads interleaved between the channel and query axes: nh = 1 is the packed [DIM, n, nouter, bh] case. bias_t is the pair bias TRANSPOSED, [n (queries), n (keys), bh] of T — QUERIES fastest, the registry's :bias_t role — so that the 32 threads of a SIMD group, which own 32 consecutive queries, read 32 consecutive elements for each key. In the keys-fastest :bias layout the same read touches 32 different cache lines; measured on an M1 Pro that single change was worth 1.3x of the forward. lse is [n, nh, nouter, B] of Float32 ([n, nouter, bh] when nh = 1). mask is [n, nouter, bh ÷ mheads] of Bool (a KEY mask per outer index, true = DROP), see mheads below; the common case is one mask per batch element, [n, nouter, B]. All raw pointers; see the note at the top of this file.

Precision

T is storage only. scale, neg_inf, every accumulator and lse are Float32, see note 3 at the top of this file for why that is a requirement and not a default.

Absent bias or mask

HB (has bias) and HM (has mask) are compile-time flags. HB = false drops the bias term from every score — one global load per (query, key), H·N³ over a triangle-attention call — and HM = false stages every in-range key as live without reading mask. The corresponding pointer is then never dereferenced, so a launcher binds any placeholder buffer: the ABI, and so the registry's buffer table, is the same for all four specialisations. HB = HM = true is the general kernel.

The dK/dV/dbias stage of :flash_mma. LuxTriangleAttention.kernel_source_tag — Method
kernel_source_tag() -> String

Short hash of the kernel sources, for a backend to put in its binary cache key.

The cache key that matters — the stage, T, dim and the tuned parameters — says what a binary was compiled FOR, not what it was compiled FROM. Without this, editing flash/forward.jl leaves every previously built binary on disk under a key that still matches, so the next run silently launches the OLD kernel: no error, no recompile, and results that quietly belong to code that no longer exists.

Computed once, when the package is precompiled, over the kernel source files — so it tracks the code actually baked into the loaded image. It does NOT cover the toolchain (Julia, GPUCompiler, KernelAbstractions, or the backend's own compiler), which can also change codegen.

LuxTriangleAttention.tune! — Function
tune!(kernel, lengths=tune_lengths(); dim, T=Float32, force=false) -> variants

Tune, compile and register a built-in kernel for each sequence length in lengths (an integer or a collection). For each length n:

  1. calibrate the device at n for (dim, T), or reuse the persisted calibration (calibrate!);
  2. pick, PER STAGE, the fastest configuration at n (choose_config);
  3. compile every stage at its configuration, for every bias / mask presence (the absent-operand specialisations are binaries of their own, so a traced call without a bias or mask never has to compile), and register them with KernelDispatch.add_variant!, keyed (dtype, dim, n, hasbias, hasmask).

A call of any length runs the variant tuned for the closest one (KernelDispatch.nearest). A length with a registered variant is skipped unless force (which also re-measures). The attention geometry (outer extent, heads) is not a key: on an M1 Pro, over triangle, MSA-row and plain-sequence shapes, the per-device choice costs at most ~10% against tuning each geometry (docs/done/FEATUREflashmma.md).

Seconds to minutes per length on a cold calibration; run it deliberately, ahead of latency-sensitive work.

LuxTriangleAttention.verification_problem — Method
verification_problem(dim, T; seed=0) -> NamedTuple

The fixed problem every candidate is checked on, with its reference results.

Small enough to cost milliseconds, shaped to reach every addressing path a configuration can get wrong: n = 67 is prime, so it is ragged against every tile and group size; nouter = 5 ≠ n exercises the rectangular strides; bh = 4 with mheads = 2 gives two batch elements with DIFFERENT masks, so a wrong batch stride on the mask is visible; the mask drops ~15% of keys and every row keeps at least one live key, except outer slice 2 of the FIRST batch mask, which drops every key (the uniform-attention path) while the second batch mask keeps it live. Operands are generated in Float64 and rounded to T once, and the reference is computed FROM the rounded values, so storage rounding is not counted as kernel error.

o, lse and delta are provided as inputs too: each backward stage is checked on its own against exact residuals, rather than inheriting whatever error the forward candidate happened to make.

LuxTriangleAttention.verification_tolerance — Method
verification_tolerance(T) -> Float64

Largest accepted max|device - reference| / max|reference| per output. Measured on the verification problem (:default, dim 16/32): Float32 ~5e-7, Float16 2–4e-4, BFloat16 2–4e-3 — the rounding of the outputs to the storage type. The bounds leave margin for reassociation and for 16-bit matrix operands (:flash_mma), and still catch any addressing or tiling error, which produces errors of order one.
